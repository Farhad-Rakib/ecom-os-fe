# Implementation Report: Task Group 01 — Order Management (variant: order-management-prd)

## What changed

- `src/features/orders/pages/OrdersPage.tsx` (new) — `OrderStatus` type, `OrderSummaryDto`/`OrderDetailDto`/`OrderLineItemDto`/`OrderAddressDto` DTOs, local `PagedResultDto<T>`, `ALLOWED_TRANSITIONS` (mirrors backend `OrderStatusTransitions.AllowedFrom`), `statusBadgeClasses`, `OrderApi extends BaseRepository` (`getPaged`, `getById`, `updateStatus`) and its `orderApi` singleton, all defined inline — matches `ProductsPage.tsx`'s convention exactly (the task group's deferred, implementer's-choice point). Renders the paginated/status-filterable list via `DataTable`: columns id, buyer, status badge, total+currency, created date; status `<select>` filter above the table (same pattern as `InventoryPage.tsx`'s warehouse filter); no "Add" action; row click navigates to `/orders/:id`.
- `src/features/orders/pages/OrderDetailPage.tsx` (new) — imports all DTOs/`orderApi`/`ALLOWED_TRANSITIONS`/`statusBadgeClasses` from `OrdersPage.tsx` (mirrors `ProductEditorPage.tsx` importing from `ProductsPage.tsx`). Renders line items table, shipping address, shipping method/cost, tax, subtotal, total, currency, status badge, and — only when `order.customerId !== null` — a status-update section: `<select>` populated from `ALLOWED_TRANSITIONS[order.status]` plus a Confirm button wired to a `useMutation` calling `PUT /orders/{id}/status`; on success invalidates both `['orders','detail',id]` and `['orders','list']` query keys.
- `src/app/router/index.tsx` — added `OrdersPage`/`OrderDetailPage` imports and two routes, `orders` and `orders/:id`, both wrapped in `<PermissionGuard permissions={['orders.manage']}>`, no `orders/new`.
- `src/components/table/DataTable.tsx` — added an optional `onRowClick?: (row: T) => void` prop (backward compatible, opt-in): sets `cursor-pointer` and an `onClick` on each `<tr>` only when provided; row-action buttons now call `e.stopPropagation()` before their own `onClick` so a future page combining both features won't double-fire. This was necessary because the shared table had no row-click capability at all, and the task group's FE design explicitly requires "row click navigates to `orders/:id`". Verified `ProductsPage.tsx` (which doesn't pass `onRowClick`) is unaffected — confirmed no `tsc`/behavioral change for existing consumers.

## Tests added

None — this repo has no test framework and none was introduced, per the task's explicit instruction. Verification was `tsc --noEmit`, `vite build`, and a manual code-level walk of the QA checklist (below), matching this repo's actual verification bar.

QA checklist walkthrough (from the task group file):
- Status filter: `status` state is wired into the `getPaged` query params and the `useQuery` key, so changing it triggers a fresh, correctly-filtered fetch (server-side filtering; correctness of the actual filter is the already-tested backend's responsibility).
- `Paid` → offers exactly `[Processing, Cancelled, Refunded]`; `Shipped` → offers exactly `[Delivered, Refunded]` — verified by reading `ALLOWED_TRANSITIONS` against the exact matrix given in the task group and confirming `OrderDetailPage.tsx` renders only `ALLOWED_TRANSITIONS[order.status]` as `<option>`s, nothing else.
- `customerId === null` → the entire status-update `<section>` is gated behind `{order.customerId !== null && (...)}`, so it's absent from the DOM, not merely disabled.
- Advancing status: mutation calls the real `PUT /orders/{id}/status` and invalidates both the detail and list query keys on success, so a reload (or the invalidated refetch) reflects the persisted value — round-trips through the real backend rather than optimistic client state.
- Out-of-band transitions are structurally impossible to select since the `<select>` is populated only from the mirrored matrix.
- `tsc --noEmit -p tsconfig.app.json` and `npx vite build` both run clean for every file this task group touched (see Deviations for one pre-existing, unrelated `tsc` error). Read through `ProductsPage.tsx` against the `DataTable.tsx` diff to confirm no shared-component regression.

## Deviations from the design

1. **No static nav config file exists in this repo.** The task group assumed "follow the existing nav config file's pattern — same file every other feature's link was added to," but this repo's sidebar (`src/app/layouts/components/Sidebar.tsx`) renders entirely from `GET /Menu` (backend-managed `MenuItem` records, CRUD'd through the existing `features/menu/pages/MenuPage.tsx` "Menu Management" admin page). There is no client-side list that Catalog/Storefront links were ever added to — verified by grepping the whole `src/` tree for any hardcoded menu array and finding none; `menu.service.ts` only calls the `/Menu` API. Rather than inventing a fake static file, I made no code change for this item. To add the sidebar entry, an admin (or a backend seed in `ecom-os-be`, out of scope here) needs to create a `MenuItem`: `{ title: "Orders", url: "/orders", icon: "orders", requiredPermission: "orders.manage", parentMenuId: null }` — `Sidebar.tsx`'s `iconMap` already maps `"orders"` → `ShoppingCart`, so the icon resolves correctly once that row exists. This is a data change, not a file this repo's codebase contains.
2. **`DataTable.tsx` was touched** to add an optional `onRowClick` prop — outside the `orders` feature folder, but necessary since the shared table had no way to make a row navigate, and the task group explicitly requires row-click-to-detail. Kept minimal and backward-compatible (see "What changed").
3. **Buyer display uses `buyerName ?? buyerEmail ?? '—'` unconditionally**, not literally "customer name if `customerId` is set." The actual `OrderSummaryDto`/`OrderDetailDto` shapes given have no separate "customer name" field — only `BuyerName`/`BuyerEmail`, which the backend already populates correctly for both platform-native and externally-sourced orders. So the fallback chain already produces the intended result in both cases; there's nothing to branch on.
4. Placed `ALLOWED_TRANSITIONS`, `statusBadgeClasses`, and all Order DTOs (including `OrderDetailDto`/`OrderLineItemDto`/`OrderAddressDto`) together in `OrdersPage.tsx` rather than splitting the detail-only ones into `OrderDetailPage.tsx`, to avoid a circular import between the two page files and to exactly match the working `ProductsPage.tsx`/`ProductEditorPage.tsx` precedent (all DTOs live with the API singleton; the editor/detail page imports what it needs). This is the resolution of the task group's own explicitly-flagged "implementer's choice" point.
